# P02 · 手写流式客户端：不引 SDK，但要能吃住空响应

| 项 | 内容 |
|---|---|
| 目标 | 服务端直连 DeepSeek，流式拿到正文与推理片段 |
| 落点提交 | `cbac5fc` feat(infra): 手写 DeepSeek 流式客户端，不引入 SDK |
| 后续修正 | `06698be`（分批策略）、`f634f25`（超时与断连） |

## 1. 我给出的指令

> "少一个依赖，就少一个评委机器上装不上的理由。自己解析 SSE 分帧。
> 推理模型的 `reasoning_content` 要单独透传出来——它是'思考可视化'唯一诚实的素材来源。"

要求：

- 不引官方 SDK，用 `fetch` + `ReadableStream`；
- 分帧必须能处理跨 chunk 的半截帧；
- 超时、客户端断开、空响应三类失败要能区分。

## 2. AI 的首版方案

`streamChat()` 用 `TextDecoder` 累积 buffer，按 `\n\n` 切帧，逐行取 `data:`，
解析 `delta.content` 与 `delta.reasoning_content`，遇 `[DONE]` 停。
结构没问题，但对"流里返回了 200、正文却是空字符串"这种情况只抛了一个笼统的 `PARSE`。

## 3. 翻车与修正（真实发生）

第一次重新录制演示数据时，前 6 题都正常，第 7 题（简答题）直接崩：

```
LlmError: 模型返回空内容
  at streamChat (server/infra/llm.ts:116)
  at runBatch (server/domain/generator.ts:178)
```

排查结论：简答题要一次性输出"完整解答 + 16 条评分细则"，
推理模型把 `max_tokens` 全花在 `reasoning_content` 上，正文被截成空。

三步修正：

1. 把空响应单独归类为 `EMPTY`，不再和 JSON 解析失败混为一谈；
2. 输出预算从 4096 提到 8000，重试时提到 12000；
3. 更关键的是改**任务切分**：简答题单独成批（`makeBatches`），单次输出规模降到可控。

改完后同一份大纲的生成从 74.7 秒降到 24.6 秒，且 0 轮修复通过。

## 4. 复盘

"加大重试次数"是最诱人的错误答案——它只是把同一个失败重放两遍。
真正有效的是**降低单次任务的规模**。这条经验后来写进了 `AGENTS.md` 的"不留死循环"条款。
